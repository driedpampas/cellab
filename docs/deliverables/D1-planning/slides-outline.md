## Part I: Team and problem

**1. Title**
- CelLab: describing, simulating and reasoning about cellular automata
- Team members, course, date

**2. Team**
- 2 members; roles not fixed yet, split by component once D2 starts
- Working agreements: shared GitHub repo, every AI conversation auto-logged into the repo

**3. The problem in one slide**
- Input: natural-language description of an automaton + initial world
- Output: simulated generations, stored and visualised, + answers to 5 questions
- Diagram: text → parser/validator → spec → simulator → question engine / storage / ML → GUI

**4. The 5 questions**
- List them; note that a finite deterministic system must eventually repeat
- So Q2, Q3 and Q5 become exactly answerable: stable = cycle of length 1, and "never occurs" is provable once a cycle closes
- Goal: all 5 questions for every supported automaton

## Part II: Understanding the automata

**5. The 15 examples: a taxonomy**
- Our view: the 15 are a benchmark, the system must be general
- 4 categories: classic synchronous / numeric-valued / moving particles / agent-based
- Visual: 4 columns with the automata grouped

**6. Difficulty map**
- Table: automaton × (simulate, answer questions, learn) with 1–5 ratings
- Callouts: randomness needs seeds; agents need extra state; diffusion needs tolerance

**7. Rule 30: the hard case**
- Simple rule, random-looking centre column, the open Rule 30 Prize problems
- Our mini-experiment: cycle length on finite rings jumps unpredictably (table: widths 8–21)
- Message: some questions have no known shortcut, and we will show where prediction breaks

## Part III: Technical solution

**8. Architecture**
- Components: spec format, validator, simulation engine, question engine, storage, ML module, GUI
- Which deliverable builds what (D2 = spec + engine + storage, D3 = ML, D4 = NL)

**9. The central idea: one automaton spec**
- Small JSON example (e.g. forest fire): states, neighbourhood, boundary, update mode, rules, seed
- 3 update modes: synchronous / ordered movement / agents
- "Expressive envelope": what we support, and what the validator rejects with a reason

**10. State space and storage**
- State space sizes (Rule 30 ring: 2^n; 50×50 grid with 3 states: 3^2500) → no enumeration, hashing instead
- Compact NumPy arrays, bit-packing for binary grids (64×64 = 512 bytes)
- Keyframes + diffs for long runs; save/restore of whole experiments (spec + seed + states)

**11. Answering the questions: 3 strategies**
- 1) Simulation + cycle detection by state hashing (exact, always)
- 2) Shortcuts from rule properties (exact, instant): conserved quantities, one-way growth, majority rules
- 3) Learned prediction (approximate, measured accuracy)
- Random automata: fixed seed or Monte Carlo statistics over many runs

## Part IV: AI components

**12. Dataset and ML experiment**
- Dataset: generated by our own simulator, so labels are exact and unlimited
- Main experiment: all 256 elementary rules, labelled by Wolfram class
- Model: shared encoder + 5 heads ("single pass") vs 5 separate models
- Hypothesis: accuracy collapses on chaotic (class III/IV) rules such as Rule 30
- Training on Google Colab (GPU), data + checkpoints on Drive, inference on laptop

**13. Natural language → spec**
- Validation as constraint checking: undeclared states, missing transitions, contradictions, missing parameters
- Three-tier parser: grammar/rule-based → small local model (JSON-constrained) → API fallback
- Bonus: fine-tune a small model on Colab with generated description/spec pairs, run it locally

**14. Tech stack**
- Python, NumPy (+ Numba if needed), PyTorch, Ollama / llama.cpp, GUI (Streamlit or PySide; to decide)
- Hardware reality: laptops without NVIDIA GPU → Colab for training, laptops for everything else

## Part V: Plan

**15. Risks and mitigations**
- Underspecified descriptions → validator asks or applies documented defaults
- Chaotic rules → report limits honestly, measure them
- Randomness → seeds + statistics
- Weak hardware → Colab, small models
- Scope (15 automata + bonuses) → general engine first, presets after

**16. Timeline**
- L3 plan (this) → L6 spec + engine + storage + questions → L11 dataset + ML → L13 NL parser → L14 final demo
- Stretch goals listed separately
